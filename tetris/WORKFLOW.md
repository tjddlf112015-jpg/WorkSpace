# 테트리스 애플리케이션 작업 절차

## 1. 기본 원칙

- `CLAUDE.md`의 요구사항과 API 계약을 기준으로 작업한다.
- 현재 프로젝트 구조와 기존 구현을 우선 존중한다.
- 한 번에 하나의 작은 기능 단위를 구현하고 즉시 검증한다.
- API 계약을 변경하면 백엔드, 프론트엔드, 테스트를 함께 수정한다.
- 비밀번호, JWT 시크릿, 액세스 토큰을 소스 코드나 로그에 남기지 않는다.
- 개발용 SQLite 데이터베이스 파일과 환경별 비밀값은 버전 관리에서 제외한다.

## 2. 작업 시작 절차

1. `CLAUDE.md`, `PLAN.md`, `WORKFLOW.md`를 읽는다.
2. 현재 브랜치와 작업 트리의 변경 사항을 확인한다.
3. 관련 파일, 엔드포인트, 모델, 테스트를 검색한다.
4. 요청사항을 작은 작업 단위로 나눈다.
5. 변경 전 현재 동작을 확인할 수 있는 가장 좁은 테스트 또는 실행 명령을 정한다.
6. 작업 범위와 완료 조건을 기록한다.

## 3. 백엔드 구현 절차

### 3.1 설정과 데이터베이스

1. 환경 변수에서 데이터베이스 URL, JWT 시크릿, 토큰 만료 시간을 읽는다.
2. SQLite 엔진과 세션을 구성한다.
3. 사용자와 게임 기록 모델을 정의한다.
4. 이메일 유일성, 외래 키, 점수 제약, 필요한 인덱스를 설정한다.
5. 개발용 데이터베이스 초기화 또는 마이그레이션 절차를 마련한다.

확인:

- 애플리케이션 시작 시 데이터베이스 연결 오류가 없는가?
- SQLite 파일이 소스 저장소에 생성되거나 커밋되지 않는가?

### 3.2 회원가입과 로그인

1. 요청 및 응답 Pydantic 스키마를 정의한다.
2. 회원가입에서 이메일 형식과 비밀번호 조건을 검증한다.
3. 이메일을 일관된 형식으로 정규화한다.
4. 비밀번호를 Argon2 또는 bcrypt로 해시한다.
5. 중복 이메일을 `409 Conflict`로 처리한다.
6. 로그인 시 사용자 미존재와 비밀번호 불일치에 같은 인증 오류를 반환한다.
7. JWT 발급과 검증을 공통 보안 모듈로 분리한다.
8. `GET /api/auth/me`에 인증 의존성을 연결한다.

확인:

- 가입 전 로그인에 실패하는가?
- 정상 로그인에서만 토큰이 발급되는가?
- 잘못된 토큰과 만료 토큰이 거부되는가?
- 응답이나 로그에 평문 비밀번호가 없는가?

### 3.3 게임 기록과 최고점수

1. 인증된 사용자에서 사용자 ID를 얻도록 의존성을 연결한다.
2. 점수와 선택 통계의 입력 범위를 검증한다.
3. 기록 시각은 서버에서 생성한다.
4. 게임 종료마다 새 레코드를 추가한다.
5. 최고점수 조회는 점수 내림차순, 기록 시각 오름차순으로 정렬한다.
6. 기록이 없을 때 사용할 빈 응답 형식을 정의한다.
7. `POST /api/games/records`, `GET /api/games/records/me`, `GET /api/scores/highest`를 문서화한다.

확인:

- 인증 없이 기록 저장이 불가능한가?
- 음수 점수가 거부되는가?
- 동일 사용자의 여러 게임이 모두 남는가?
- 서로 다른 사용자의 기록을 합산해 최고점수를 계산하는가?
- 동점이면 먼저 저장된 기록이 선택되는가?

## 4. 프론트엔드 연동 절차

1. API 기본 URL을 환경 변수로 구성한다.
2. 회원가입 요청과 입력 오류를 연결한다.
3. 로그인 성공 시 JWT를 안전한 방식으로 관리한다.
4. 보호 API 요청에 인증 헤더를 추가한다.
5. `401 Unauthorized`를 인증 만료 상태로 변환한다.
6. 로그인하지 않은 사용자의 기록 저장 시 로그인 화면 또는 안내로 연결한다.
7. 게임 종료 처리에서 기록 저장 요청이 한 번만 발생하도록 보장한다.
8. 기록 저장 성공 후 최고점수를 재조회한다.
9. 로딩, 오류, 빈 상태, 네트워크 실패를 각각 처리한다.
10. 최고점수와 사용자 식별 정보를 화면에 표시한다.

확인:

- 새로고침 후 인증 상태 처리 방식이 일관적인가?
- 게임 종료 이벤트가 중복 호출되어 기록이 두 건 저장되지 않는가?
- 기록 저장 실패가 게임 화면을 망가뜨리지 않는가?
- 최고점수 기록이 없을 때 빈 상태가 자연스럽게 보이는가?

## 5. 테스트 실행 순서

작은 범위에서 큰 범위 순서로 실행한다.

1. 변경한 함수 또는 모듈의 단위 테스트
2. 관련 백엔드 API 테스트
3. 인증부터 최고점수까지의 백엔드 통합 테스트
4. 프론트엔드 API 클라이언트 및 상태 테스트
5. 회원가입부터 게임 기록·최고점수 갱신까지의 핵심 흐름 테스트
6. 전체 테스트 명령

기본 명령 예시:

```bash
pytest
uvicorn app.main:app --reload
```

## 6. API 변경 절차

API 요청 또는 응답을 변경해야 할 경우 다음 순서를 따른다.

1. 변경 이유와 호환성 영향을 기록한다.
2. Pydantic 스키마와 라우터를 수정한다.
3. OpenAPI 설명과 예시를 수정한다.
4. 백엔드 테스트를 수정하거나 추가한다.
5. 프론트엔드 타입과 API 클라이언트를 수정한다.
6. 프론트엔드 상태 처리와 화면을 수정한다.
7. 전체 핵심 흐름을 다시 검증한다.

## 7. 오류 및 보안 점검

- 잘못된 입력은 `422 Unprocessable Entity`로 처리한다.
- 인증 실패는 `401 Unauthorized`로 처리한다.
- 중복 이메일은 `409 Conflict`로 처리한다.
- 내부 예외, SQL 오류, 스택 트레이스를 사용자 응답에 노출하지 않는다.
- 존재하지 않는 이메일과 잘못된 비밀번호를 구분해 응답하지 않는다.
- JWT 알고리즘과 만료를 검증한다.
- CORS는 허용된 프론트엔드 출처만 지정한다.
- 점수는 0 이상으로 검증하며 클라이언트 입력 신뢰의 한계를 문서화한다.
